# PF-083 — API keys for service-to-service calls

**Spec:** `docs/DECISIONS.md` ADR-036, and the PF-083 entry in `docs/BACKLOG.md`. Those two are the
authority; where this plan disagrees with them, they win.

**Branch:** `m0-api-keys`, cut from `m0-week9-plan`. **Module:** M0 Platform / Auth.

## Context

Browsers already authenticate with a Supabase JWT in httpOnly cookies, verified per request by
`getSession()` in `src/lib/session.ts`. Nothing that is not a browser can authenticate at all today.
This task adds workspace API keys for the Jira sync, CI smoke tests and the owner's own scripts.

The decision that shapes everything: **a key acts as the member who created it.** Every RLS policy in
this database is written against `auth.uid()`, so a standalone service identity would need a second
policy on about twenty tables. Binding the key to its issuer sends the request down the existing
`actAs(user_id)` → `withUser` path, and tenant isolation, role checks, the frozen-approved rules and
the audit log all keep working untouched.

## Global Constraints

These bind every task. They come from `CLAUDE.md` and ADR-036.

1. **The plaintext key is never stored and never logged.** Only a SHA-256 hash and a short
   non-secret prefix. It is shown to the user exactly once, in the response that creates it.
2. **Key format:** `pf_<env>_<prefix>_<secret>` where `<env>` is `live` or `test`, `<prefix>` is 8
   lowercase base32 characters used for lookup and log correlation, and `<secret>` is 32 bytes from
   `crypto.randomBytes` in base64url. Compare the hash with `crypto.timingSafeEqual`.
3. **Effective role is the lower of the key's scope and the member's role, read at request time.**
   A key never grants a role its owner does not have, and removing or demoting the member narrows or
   kills the key on the next request.
4. **Scopes are `read` and `write` only. No key can approve anything.** Approve and confirm routes
   refuse a key with 403 whatever its owner's role, because CLAUDE.md §7.7 reserves APPROVED for a
   user action.
5. **Keys authenticate `/api/*` only.** `/dashboard/*` never accepts one.
6. Every table with project data has `workspace_id` and an RLS policy, and each new policy gets an
   integration test (CLAUDE.md §7.9).
7. No new dependency. Everything here is in `node:crypto`.
8. `pnpm lint`, `pnpm typecheck` and `pnpm test` must pass. Tests cannot run in Claude's VM — see
   "Verification" below.

## Task 1 — The `api_keys` table, its policies and its repository

**Files:** `src/db/schema.ts` (add the table), `src/db/migrations/0010_api_keys.sql`,
`src/modules/api-keys/schema.ts`, `src/modules/api-keys/repository.ts`,
`src/modules/api-keys/store-repository.ts`, `src/modules/api-keys/pg-repository.ts`,
`tests/integration/db/api-keys-data.test.ts`.

**Columns.** `id` uuid primary key; `workspace_id` uuid not null; `user_id` uuid not null references
`auth.users`; `name` text not null; `prefix` text not null; `secret_hash` text not null; `scope` text
not null check in (`read`, `write`); `created_at` timestamptz not null default now();
`last_used_at` timestamptz; `expires_at` timestamptz not null; `revoked_at` timestamptz.

- A composite foreign key `(workspace_id, user_id)` to `workspace_members(workspace_id, user_id)`,
  matching how the other tables keep a row inside one workspace (ADR-026). `on delete cascade`, so
  removing a member destroys their keys.
- A unique index on `prefix`.
- An index on `(workspace_id, user_id)`.
- `expires_at` is mandatory. The service defaults it to 90 days out when the caller gives none.

**RLS.** Enable it, and follow `0004_discovery_data.sql` for the shape of the policies and the
`private.*` SECURITY DEFINER membership helpers (writing membership checks inline caused "infinite
recursion detected in policy" in PF-012 — use the helpers).

- select: a member sees their own keys; owners and admins see every key in the workspace.
- insert: a member inserts a key for themselves only (`user_id = auth.uid()`), in a workspace they
  belong to.
- update: only to revoke, and only a key the caller may see. `last_used_at` is also an update, so
  the policy must allow it for the key's own user.
- delete: refused outright. Keys are revoked, never deleted, so the audit trail survives.

**Repository interface.** Mirror `src/modules/workspaces/repository.ts`: an interface, a
`store-repository.ts`, a `pg-repository.ts`, and a facade picking by `dataBackend()`. Every method
takes a `Scope` or `WorkspaceScope` first.

```ts
listForUser(scope: WorkspaceScope, userId: string): Promise<ApiKey[]>
listForWorkspace(scope: WorkspaceScope): Promise<ApiKey[]>
insert(scope: WorkspaceScope, key: ApiKey): Promise<ApiKey>
revoke(scope: WorkspaceScope, id: string, at: string): Promise<ApiKey>
/** Lookup for the auth path. Runs as the admin client: the caller is not yet authenticated. */
findByPrefix(prefix: string): Promise<ApiKeyWithSecret | null>
touchLastUsed(id: string, at: string): Promise<void>
```

`findByPrefix` and `touchLastUsed` are the two that cannot take a user scope, because at that moment
nobody is signed in. They use `adminDb()` from `src/db/client.ts` and must select only the columns
the verify path needs. Put a comment on each saying why it bypasses RLS and that it must never be
called from a route.

**`ApiKey`** never carries `secretHash`. Make `ApiKeyWithSecret` a separate type used only inside the
verify path, so a leak into a response is a type error.

**Tests** (`tests/integration/db/api-keys-data.test.ts`, PGlite, following
`tests/integration/db/rls-writes.test.ts`): a member can insert and list their own key; a member
cannot see another member's key; an owner sees both; a foreign workspace sees none; a delete is
refused; revoking works; `(workspace_id, user_id)` is enforced so a key cannot point at a member of
another workspace.

**Done when:** the migration applies on PGlite, the repository round-trips in both backends, and the
RLS tests above pass — each asserting the actual refusal, not merely that an error was thrown.

## Task 2 — Minting, verifying and enforcing a key

**Files:** `src/lib/api-key.ts`, `src/modules/api-keys/service.ts`,
`src/modules/workspaces/service.ts` (the key branch of `currentContext`), `src/lib/supabase/proxy.ts`
(let a key through the gate), `proxy.ts` if a surface header is needed,
`app/api/workspace/api-keys/route.ts`, `app/api/workspace/api-keys/[id]/route.ts`,
`tests/unit/lib/api-key.test.ts`, `tests/integration/api/api-keys.test.ts`, and the role list in
`tests/integration/api/route-matrix.test.ts`.

**`src/lib/api-key.ts`** — pure, no database, fully unit-tested:

```ts
export const KEY_PREFIX_LENGTH = 8;
export function mintApiKey(env: "live" | "test"): { plaintext: string; prefix: string; hash: string }
export function parseApiKey(header: string | null): { prefix: string; secret: string } | null
export function hashApiSecret(secret: string): string          // sha256, hex
export function secretMatches(secret: string, hash: string): boolean   // timingSafeEqual
export function isApiKeyHeader(header: string | null): boolean  // cheap check for the gate
```

`parseApiKey` returns null for anything malformed — wrong scheme, wrong number of parts, wrong
prefix length, characters outside the alphabet. It must not throw on hostile input.

**`service.ts`:**

- `createApiKey(ctx, { name, scope, expiresAt? })` — any member may create a key for themselves. A
  `write` scope is refused if the member's role cannot write. Returns the `ApiKey` plus the
  plaintext, which only this one return value ever carries. Audit `api_key` / `created`.
- `listApiKeys(ctx)` — the caller's own keys, plus the whole workspace's for owners and admins.
- `revokeApiKey(ctx, id)` — sets `revoked_at`. A member revokes their own; owners and admins revoke
  any in the workspace. Audit `api_key` / `revoked`. Revoking an already-revoked key is idempotent.
- `contextForApiKey(header)` — the verify path, in this order, and **every failure returns the same
  `UNAUTHORIZED` with the same message**, so the response never says which step failed:
  1. `parseApiKey`; null → fail.
  2. `findByPrefix`; missing → fail.
  3. `secretMatches`; false → fail.
  4. `revoked_at` set, or `expires_at` in the past → fail.
  5. Read the membership for `(workspace_id, user_id)`. None → fail (the member was removed).
  6. Build the `WorkspaceContext`: `session` is `{ userId, name: "<key name> (API key)", email: "" }`,
     `workspace` is the row's workspace, `role` is the lower of the key's scope and the member's role.
  7. `touchLastUsed`, which must not fail the request if it errors — log and continue.

  **Do not call `ensureWorkspace`**: it creates a workspace when the user has none, and a key must
  never create one. Read the membership directly.

**Role ceiling.** `scope: "read"` maps to a role that passes no write check. Add
`effectiveRole(scope, memberRole): Role` next to `MANAGER_ROLES` in `src/lib/auth.ts` and unit-test
its table: a `read` key always lands on a role that `requireRole` refuses for writes; a `write` key
keeps the member's role but never gains one.

**No approvals.** Add `refuseApiKeyApproval(ctx)` and call it in the approve and confirm services —
`approvePrd`, `approveReadyStories` and the story approve path, `confirmDiscovery`, and the change
approve path. Mark the context so the check can tell a key from a cookie: add
`viaApiKey?: true` to `WorkspaceContext` and set it only in `contextForApiKey`. Grep for the approve
and confirm entry points rather than trusting this list, and say in your report which ones you found
and guarded.

**The gate.** In `src/lib/supabase/proxy.ts`, a request to `/api/*` carrying a key header passes the
gate without a cookie session — `gate(request.nextUrl, Boolean(data?.claims) || isApiKeyHeader(...))`.
Middleware does no database work; the route verifies. Keys must not reach `/dashboard/*`, so
`currentContext` honours a key only for an API request: set a header in `proxy.ts` marking the
surface, or read the pathname where `currentContext` can see it, and say in your report which you
chose and why.

**`currentContext`.** Before `getSession()`, if the request carries a key header on an API surface,
return `contextForApiKey`. Otherwise the existing path, unchanged. Keep the `react` `cache()`
wrapper. The `getSession` import is lazy on purpose (scripts must not load `next/headers`) — keep it
that way, and import whatever you add the same way if it reaches into `next/headers`.

**Routes.** `POST /api/workspace/api-keys` creates one, `GET` lists them,
`DELETE /api/workspace/api-keys/[id]` revokes. Route handlers stay thin and call the service only
(CLAUDE.md §6). The create response is the only place the plaintext appears.

**Tests.** Unit: minting, parsing (including hostile input), hashing, constant-time comparison, the
role-ceiling table. Integration: create → authenticate with the plaintext → read a project; a
`read` key is refused on a write route; a revoked key, an expired key and a key whose member was
removed are each refused with the same message; a key is refused on an approve route even for an
owner; a key is refused on a `/dashboard` path. Add the new write routes to the `MEMBER_WRITES`
list in `route-matrix.test.ts` so the matrix covers them.

**Done when:** every test above is written, `tsc` and `eslint` are clean, and no test or log line
contains a plaintext key.

## Task 3 — The settings screen, the audit trail and the architecture note

**Files:** `app/dashboard/settings/api-keys/page.tsx`, `components/settings/api-keys-panel.tsx` (plus
smaller components if it would pass 300 lines), `src/modules/audit/schema.ts` if the entity type
needs adding, `docs/ARCHITECTURE.md`, `.env.example` if a variable is added.

- A list of the caller's keys: name, prefix, scope, created, last used, expiry, and a Revoke button.
  Owners and admins also see other members' keys, labelled with whose they are.
- Create: a name, a scope, an optional expiry. On success the plaintext is shown once, with a copy
  button and a line saying it will not be shown again. It must not survive a re-render or a refetch.
- Revoke asks for confirmation and says the key stops working at once.
- An empty state explaining what a key is for and that it acts as the member who made it.
- UI must not import `src/ai` or the database (the ESLint rules enforce this).
- `docs/ARCHITECTURE.md` gains an auth section: JWT sessions for people, member-bound keys for
  services, the role ceiling, and no approvals by key.

**Done when:** the page lists, creates and revokes; the plaintext appears exactly once; `tsc` and
`eslint` are clean; `docs/ARCHITECTURE.md` describes the model.
